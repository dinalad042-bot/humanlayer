Great question. Yes, **as written it works on a single `RESEARCH_TRACKING.md` file** — but that's actually a problem for larger projects. Let me break down why and give you the upgraded version: ## The Problem with One Doc - For a small task → one doc is fine - For a large codebase or complex feature → **one doc becomes a giant mess** - Claude's context window gets cluttered re-reading a massive single file - Different research areas get tangled together ## The Solution: Multi-Doc Structure Here's the upgraded version that uses a **folder system** — one index doc that tracks everything, and separate docs per research area: --- ```markdown # Tracked Codebase Research → Implementation Plan (Multi-Doc) You are conducting a systematic, self-tracked research process across this codebase. You produce a final "Tracked Research & Implementation Plan" that is comprehensive, accurate, and leaves nothing unresolved. You use a FOLDER of documents, not a single file, to stay organized. --- ## DOCUMENT STRUCTURE Create a folder called `research/` (or user-specified location) with this layout: ``` research/ ├── INDEX.md ← Master tracker (your command center) ├── areas/ ← One doc per research area │ ├── 01-area-name.md │ ├── 02-area-name.md │ └── ... ├── questions.md ← All open questions consolidated └── PLAN.md ← Final implementation plan (created last) ``` --- ## FILE: research/INDEX.md (Master Tracker) This is your command center. It tracks EVERYTHING at a glance. ```markdown # Research Index ## Goal [User's stated goal] ## Status: 🔴 IN PROGRESS ## Research Areas | # | Area | Status | Doc | Key Finding | |---|------|--------|-----|-------------| | 1 | [Area name] | 🔴 Not started | [01-area-name.md](areas/01-area-name.md) | — | | 2 | [Area name] | 🟡 In progress | [02-area-name.md](areas/02-area-name.md) | — | | 3 | [Area name] | 🟢 Complete | [03-area-name.md](areas/03-area-name.md) | [Brief finding] | ## Current Position 📍 [What you're doing right now] ## Discovery Log (Chronological) - [timestamp] Found X in `file.py:42` → added to Area 3 - [timestamp] Area 1 complete — main pattern is Y - [timestamp] New area discovered: need to research Z → added Area 5 ## Open Questions Count: [N] See [questions.md](questions.md) ## Blockers - [ ] ⚠️ [Anything blocking progress] ``` --- ## FILE: research/areas/NN-area-name.md (Per-Area Research) One file per research area. This keeps findings organized and prevents one giant doc. ```markdown # Research Area: [Area Name] ## Status: 🟡 In Progress ## What I Need To Learn [Specific questions this area should answer] ## Files Examined - [ ] `path/to/file.py` — [Why examining this] - [x] `path/to/other.py` — [What I found] - [x] `path/to/third.py:45-90` — [What I found] ## Findings ### [Sub-topic 1] - **Location**: `src/module/file.py:23-45` - **What it does**: [Description] - **How it works**: [Detail] - **Connects to**: [Other areas/files] ### [Sub-topic 2] - **Location**: `src/other/file.py:10-30` - **What it does**: [Description] ## Code Patterns Observed - Pattern: [Description] — seen in `file1.py:10`, `file2.py:20` ## Relevance to Implementation [WHY this matters for the final plan] ## New Questions Generated - [Question] → sent to questions.md - [Question] → spawned new area NN ## Status Update - [x] Initial investigation - [x] Deep dive into [component] - [ ] Trace data flow through [system] - [ ] Verify [assumption] ``` --- ## FILE: research/questions.md (Consolidated Questions) ```markdown # Open Questions ## Answerable by Code (Need More Research) - [ ] [Question] — likely in `src/somewhere/` → assigned to Area [N] - [ ] [Question] — need to trace from `file.py:30` → assigned to Area [N] ## Need Human Input - [ ] ⚠️ [Question] — can't determine from code alone - [ ] ⚠️ [Question] — business logic decision ## Resolved - [x] [Question] — Answer: [answer], found in `file.py:55` (Area [N]) - [x] [Question] — Answer: [answer], confirmed by user ``` --- ## CORE LOOP (Same logic, multi-doc execution) ### PHASE 1: INITIALIZE 1. Ask the user for their goal, known relevant files, and constraints 2. Create the `research/` folder structure 3. Analyze the goal and break it into research areas 4. Create `INDEX.md` with initial areas listed 5. Create empty area docs for each area 6. Create empty `questions.md` 7. Update `INDEX.md` Current Position → "Starting Area 01" ### PHASE 2: RESEARCH LOOP For each area: **Step A: Start the area** - Update `INDEX.md` → set area status to 🟡, update Current Position - Open the area doc, fill in "What I Need To Learn" **Step B: Investigate** - Read files FULLY — do not skim - Trace imports, data flow, dependencies - Note specific file:line references **Step C: Record in the area doc** - Check off files examined - Write findings with file:line references - Document code patterns - Write why it matters for implementation - Log any new questions → add to `questions.md` - If new research areas discovered → create new area doc + add to `INDEX.md` **Step D: Complete the area** - Update area doc status to 🟢 Complete - Update `INDEX.md`: - Set area status to 🟢 - Fill in Key Finding column - Add entry to Discovery Log - Update Current Position to next area - Update Open Questions Count **Step E: Check what remains** - All areas 🟢? → Go to PHASE 3 - Areas remain? → Go to Step A for next area ### PHASE 3: RESOLVE QUESTIONS Review `questions.md`: - "Answerable by Code" items → create new areas or revisit existing ones → back to PHASE 2 - "Need Human Input" items → ask the user, record answers - Move all resolved items to the Resolved section - When all answerable questions resolved → PHASE 4 ### PHASE 4: WRITE THE PLAN Create `research/PLAN.md`: ```markdown # Implementation Plan ## Overview [What we're building and why] ## Research Summary Based on [N] research areas investigated. Full research at: - [Link to each area doc with one-line summary] ## Current State Analysis [Synthesized from all area docs — with file:line refs] ## Desired End State [What success looks like + verification method] ## Out of Scope [What we're NOT doing] ## Implementation Phases ### Phase 1: [Name] **Goal**: [What this achieves] **Research basis**: [Which area docs informed this] **Changes**: | File | Change | Why | |------|--------|-----| | `path/file.py:23` | Modify function X | [Reason from research] | | `path/new.py` | Create new | [Reason from research] | **Detailed changes**: [Code snippets or precise descriptions] **Success criteria**: Automated: - [ ] `command to run` Manual: - [ ] [What to verify] **Depends on**: Nothing --- ### Phase 2: [Name] [Same structure] **Depends on**: Phase 1 --- [Continue for all phases] ## Testing Strategy [Derived from research findings] ## Risks [Based on complexity/patterns found during research] ## All Files Referenced [Complete list from all area docs] ``` Update `INDEX.md` status to 🟢 COMPLETE. --- ## CRITICAL RULES 1. **Update INDEX.md EVERY time you finish an area or change focus.** It's your persistent memory. 2. **One area doc per research topic.** Don't cram unrelated findings into one doc. If an area gets too broad, split it. 3. **Every finding needs a file:line reference.** No vague references. 4. **Questions go to questions.md IMMEDIATELY when discovered.** Don't hold them in your head. 5. **New discoveries = new areas.** If investigating Area 2 reveals you need to understand something unexpected, create Area N+1 and add it to the index. 6. **Never write PLAN.md with open answerable questions.** Resolve them first or mark them as needing human input. 7. **The INDEX.md Discovery Log is chronological.** It tells the story of your research journey. Always append, never rewrite it. 8. **Cross-reference between area docs.** If Area 3 findings relate to Area 1, note it in both docs. 9. **Read files FULLY.** Never partial-read and assume. 10. **Each area doc must have a "Relevance to Implementation" section.** If you can't explain why it matters, you're researching the wrong thing. --- ## GETTING STARTED Ask the user: > I'll conduct a tracked, multi-document research process across your codebase and produce a complete implementation plan. > > I'll create a `research/` folder with: > - **INDEX.md** — master tracker showing all progress at a glance > - **Area docs** — one per research topic with detailed findings > - **questions.md** — consolidated questions and their resolutions > - **PLAN.md** — final implementation plan built from proven research > > Please provide: > 1. **What you want to build/change/understand** > 2. **Any files or areas you know are relevant** (optional) > 3. **Any constraints** (optional) > 4. **Where to put the research folder** (default: `./research/`) Then follow the phases exactly. ``` --- ## Quick Comparison | | Single Doc | Multi-Doc (above) | |---|---|---| | Small task (< 5 files) | ✅ Perfect | Overkill | | Medium feature (5-20 files) | 😐 Gets messy | ✅ Clean | | Large system (20+ files) | ❌ Unmanageable | ✅ Organized | | Resumability | 😐 One long scroll | ✅ Pick up any area | | Claude context usage | ❌ Re-reads everything | ✅ Reads only relevant area doc | | Proof of completeness | 😐 Buried in text | ✅ INDEX table shows status instantly | **Use the single-doc version for quick tasks. Use this multi-doc version for anything substantial.**
